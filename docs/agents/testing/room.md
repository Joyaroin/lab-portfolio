## Frame-cost baseline
The cost of the landscape overview's frames, measured by `scripts/frame-cost.mjs` (#378), so the surface tickets (#381-#384) repeat the same measurement and post theirs against it. Not a spec: it is a script, run by hand through `heavy`, and no test fails on it.
- **The method.** Build the branch and serve it on your port (`npm run build`, then `npm run preview -- --port $TEST_PORT`), and in another shell run `TEST_PORT=<port> heavy node scripts/frame-cost.mjs` (one worker: the script runs one browser at a time). It runs 5 times. Each run opens a fresh Chromium (headless, as Playwright launches it, MediaSafe's host unresolvable) at **1280×720**, the landscape overview, waits for the boot screen to go and the meter bar to show, waits 8 s (the power-on and the camera's glide), then reads the browser's CPU time (CDP `SystemInfo.getProcessInfo`, the sum over the browser, GPU and renderer processes) and the number of frames drawn (WebGL `clear` calls, one per frame) at the start and the end of a **10 s window** with nothing touched, so the only frames are the ambient surfaces' ticks. It prints frames a second, CPU ms a second and **CPU ms a frame** per run, and the **median of the 5 runs** of each. The CPU ms a frame is the number to compare.
- **Baseline, today's three screens (2026-11-18, the Mac, branch ticket-378 before any surface is filled; its three screens draw exactly as before):** median **12.1 frames/s, 2929 CPU ms/s, 242.0 CPU ms/frame** (runs: 243.3, 239.4, 242.0, 240.5, 245.2 CPU ms/frame). A Mac number doesn't predict the CI runner's (its WebGL draws on llvmpipe).
- **A surface ticket** fills its placeholder, repeats the method on its own branch and posts its median CPU ms a frame against this baseline in its PR, with the machine load it ran under. If the method's numbers rise by a lot, say by how much; it does not decide whether a release spec will fail.
- **The proof** is one release the orchestrator starts by hand on `main` after #381-#384 have all merged (Adham, 2026-11-18). If a `@timing` or `@render` spec fails there on frame cost, the ticket that caused it reopens with the numbers, and no limit is loosened.
