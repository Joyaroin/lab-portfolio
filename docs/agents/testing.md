## Kinds of test
| Kind | How to select it | Where it runs |
|---|---|---|
| Unit | `npm test` | Builder and CI |
| Light browser | `make browser-light PW_ARGS=<spec>` for the specs it touched. `make browser-light` alone only for a change to shared code, through `heavy` | Builder (the specs it touched), and the release's `browser-light` job after staging. PR CI doesn't run it |
| Timing | `@timing` | The release's `browser` job, before staging. In the session only to measure or break-check, through `heavy`, 1 worker. Exact durations are unit tests that pass the time in or fake the clock (`src/frames.test.ts`, `src/tear.test.ts`, `src/nixie.test.ts`, `src/meter-power.test.ts`, `src/shift/shift.test.ts`, `src/ambient/redraw.test.ts`); browser timing specs check that a play happened, its order, and the safe side of a limit |
| Heavy rendering | `@render` | The release's `browser` job, before staging |

## What CI runs
CI runs on every branch except `staging` and `production`, including `main` after each merge. CI runs no browser specs (#352): a PR's browser job delayed its review, so the release runs them all, the release specs before staging moves and the light specs after (see below), and a failure is found and fixed there. The release runs only when started by hand, so those specs run on `main` only then, not on each merge. This partly reverses #323: a breakage in a page a PR didn't touch is no longer caught before the merge. The builder still runs the light browser specs it touched in its own session. Nothing waits for the run on `main`. The runner takes 3 jobs at a time (adham/core-infra#5; at 2 jobs, release runs 526 and 527 overlapped and took 859 s and 795 s, against about 450 s alone), so a release's `@timing` and `@render` specs fail on correct code when other jobs share it (#349). A release job therefore runs alone: see "The runner gate" below. With no open PR, the posting steps log that there is nothing to post and pass, except on `main`: there each failure report is added as a new comment on the standing "CI failures on main" issue (created or reopened if needed).
- `frontend`, `backend`, `integration`: the make targets of the same name
- `screenshots`: the overview plus every station, at desktop and phone size, posted to the PR
- `secret-scan`: gitleaks over the full history
- `facts`: `make facts`
- Every job starts with the runner gate, right after checkout: `node scripts/runner-gate.mjs ci` waits while a `release.yml` job that started before it is running (see "The runner gate" below)

## What release runs
`release.yml` runs only when started by hand (`workflow_dispatch`, #355), never on a merge to `main`: Forgejo's "Run workflow" on `main`, or `POST /repos/projects/lab/actions/workflows/release.yml/dispatches` with `{"ref": "main"}`. A merge doesn't release or move staging; run it again by hand to try again after a flaky failure (Forgejo can't re-run one job). The `staging` job pushes only when the run's commit is `main`'s tip, so a run started on another branch can't move staging. Staging moves only when `image` and `browser` (the release specs) both pass, so a commit whose release specs failed never reaches staging. The light specs run after staging, so a light failure on `main` doesn't hold staging back. Each failure is a comment on the "CI failures on main" issue, and `main` stays red until a fix or a revert merges.
- `image`: builds and pushes the image
- `browser`: the release specs only (`make browser-release`: `@timing` and `@render`), on 3 workers (`playwright.config.ts`). The runner has no GPU, so WebGL draws on Mesa's llvmpipe under Xvfb (a third of SwiftShader's CPU); `tests/webgl.spec.ts` fails it if Chromium falls back to SwiftShader
- Each browser job's last step (`browser` and `browser-light` in `release.yml`), `scripts/browser-report.mjs` (its own script, not `post-ci-failure.mjs`, so its step has its own workflow assertions), reports what the run cost, pass or fail, and never changes the job result. It reads the Playwright JSON report, the job's start file and `loadavg()`. The workflows no longer run it on a PR (the script still can): it would create or update one marked comment (`<!-- ci-browser-report -->`): on a pass the job's time, the load average, flaky tests with their first error, the 10 slowest tests and the median and total `boot-ms`; on a failure a line saying the run failed and linking the failure comment. On `main` it posts only for a pass with at least one flaky test (a comment on "CI failures on main"); a clean pass writes nothing, and a failure's own comment (`post-ci-failure.mjs`) names the flaky tests, so the report posts nothing. A flaky test is one that failed and then passed on a retry (status `flaky` in the report); failure comments never count it as failed. `scripts/browser-report.test.mjs` runs it against fixture reports and a fake Forgejo
- `staging`: moves the `staging` branch to the commit, then warns if the release was slow. When main has moved past the commit, it pushes nothing and the run still passes, but the log line is a `::warning::` and `scripts/staging-skipped.mjs` comments on the standing "CI failures on main" issue (created or reopened if needed): staging did not move, which commit it still runs (read from the image tag on the `staging` branch's head, which the move step passes out as `seen` and `runs`) and that a new release on main is needed, since nothing else will move it. That step is best effort (`continue-on-error`; a failed API call is logged and exits 0). `scripts/staging-skipped.test.mjs` runs it against a fake Forgejo: a skip posts the comment, a move posts none, a failing or unreachable Forgejo still exits 0. A release can't run on a PR, so that test is the proof
- `browser-light`: needs `staging` and runs only when staging moved (the `staging` job's `moved` output is `true`; not when main had moved past the commit: that release is out of date, so start a new one on main). Runs the light specs (`make browser-light`) with the same setup, failure posting and report as the `browser` jobs, so within one release they don't share the runner with the `@timing` specs. Nothing waits for it. A failure is a comment on "CI failures on main", and `main` stays red until a fix or a revert merges
- The release clock runs from the release run's start (Forgejo's runs API, by the API run id, not the run number) to the end of the staging push. `scripts/release-clock.mjs` warns, as a comment on the standing "Browser job times" issue (created or reopened if needed), exactly when staging moved, the `browser` job retried no test (a test with more than one result in its Playwright JSON report, flaky or not) and the clock is over 360 s. The comment carries the clock, the browser job's load average and the runner wait in seconds. The warning step is best effort and never blocks staging. `scripts/release-clock.test.mjs` sweeps the rule over time, retried and moved; if the job's token can't read the runs API, the clock starts at the earlier of the `image` and `browser` job starts

- The `gate` job runs first and `image` and `browser` need it: the runner gate (see below) for the whole release. `image` has no gate step of its own, since it runs in the kaniko container, which has no node and no checkout. Within one release run, `image` (the kaniko build) and `browser` (the release specs) still run at the same time, because a run's own jobs don't block each other. `browser`, `staging` and `browser-light` start with a gate step too, since a CI job can start in the seconds between the `gate` job ending and them starting

## The runner gate
A release job is the only job running on the runner (#361, Adham's decision on 2026-11-17). Forgejo has no exclusive job and a job can't pause the runner, so the jobs coordinate through the API: the gate step reads `GET /repos/{owner}/{repo}/actions/tasks?status=running` with the job's own token (`secrets.GITHUB_TOKEN`) and decides. `scripts/runner-gate.mjs` holds the rule as one pure function, `decide`, and `scripts/runner-gate.test.mjs` (in `npm test`) tests it.
- A release job (`gate`, `browser`, `staging`, `browser-light`) waits until no other job is running in the repo that started before it and isn't part of its own run (same workflow and run number). Jobs that started after it are ignored.
- A CI job (every `ci.yml` job) waits while a `release.yml` job that started before it is running. This is narrower than "while any release job is running": a CI job that was already running when a release job started gets to finish, and the release job waits for it, so it must not wait for that release job back.
- One order covers all jobs: earlier start second first; in the same second a release job comes before any other job; then the lower task id. A job only waits for a job ahead of it, so two jobs can never wait for each other, including two that start in the same second. The tests sweep every pair of kinds, start offsets and id orders for this. Between two release jobs a CI job may run; it never runs at the same time as one.
- It polls every 10 s and gives up, failing the job, after 60 minutes of waiting, saying what it waited for. Three failed reads in a row of the task list (a token that can't read it gives HTTP 403) also fail the job. A waiting job holds a runner slot and uses no CPU.
- Each gate logs one line in the job log: `runner gate: release job waited 100 s for ci.yml #700 frontend, then went`, or `... did not wait`. Time spent waiting in a gate counts toward the release clock (it runs from the run's start), and the gate's log line says how long it waited. A CI job's or a browser job's own time in its report includes its wait, since its gate comes after `Record start time` and checkout.
- The gate comes right after `actions/checkout`, not first: the script is in the repo. A failed gate isn't in a failure comment's `STEPS`, so that comment names the job as the failed step; the reason is in the job log.
- Not covered: `adham/project-template`'s CI also uses the runner, and its jobs don't wait. A job waiting in a gate for a release job that never ends (a crashed runner) fails after 60 minutes. A `promote.yml` job has no gate: it can run beside a release job, but a release job started after it waits for it.
- Release jobs run only when started by hand, so the gate on a release job can't be seen running on a PR. The unit tests are its proof, and the first release after the change is its first real run.

`promote.yml` moves `production`, run by Adham.
