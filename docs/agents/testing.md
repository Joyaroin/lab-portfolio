## Kinds of test
| Kind | How to select it | Where it runs |
|---|---|---|
| Unit | `npm test` | Builder and CI |
| Light browser | `make browser-light PW_ARGS=<spec>` for the specs it touched. `make browser-light` alone only for a change to shared code, through `heavy` | Builder (the specs it touched), and the release's `browser-light` job after staging. PR CI doesn't run it |
| Timing | `@timing` | The release's `browser` job, before staging. In the session only to measure or break-check, through `heavy`, 1 worker. Exact durations are unit tests that pass the time in or fake the clock (`src/frames.test.ts`, `src/tear.test.ts`, `src/nixie.test.ts`, `src/meter-power.test.ts`, `src/shift/shift.test.ts`, `src/ambient/redraw.test.ts`, `src/ambient/phase.test.ts`, `src/ambient/desk-phone.test.ts`, `src/ambient/clock.test.ts`); browser timing specs check that a play happened, its order, and the safe side of a limit |
| Heavy rendering | `@render` | The release's `browser` job, before staging |

## Commands
- `make frontend`: `npm ci`, the typecheck, `npm test` (also writing vitest's JSON report, to the file the `frontend` recipe in the `Makefile` names, which `scripts/slow-tests.mjs` reads) and the build
- `npm run build`: runs `scripts/save-gap.mjs` and `scripts/save-commits.mjs` before the type check. Each reads GitHub anonymously with a 5 s timeout and writes a gitignored `src/*-saved.local.json`. A failed call keeps the saved file: the newer of the local and committed files by `savedAt`, so a build offline or past the rate limit still leaves a valid file. `COMMITS_API=<url>` replaces the commits URL, for the offline run: `COMMITS_API=https://invalid.example heavy npm run build`. Run builds through `heavy`
- `make integration`: `make frontend`, then the integration test
- `make browser`: the full Playwright suite. Installs browsers and system packages only in CI, and in the CI image (`ci/Dockerfile`, which release.yml's browser jobs run in) only a browser the image lacks. CI never runs it whole: the release runs the two selections below
- `make browser-light`: the `browser` recipe without the release specs. Passes `PW_ARGS` through
- `make browser-release`: the `browser` recipe with only the release specs, `@timing` or `@render`. Passes `PW_ARGS` through. Both targets take the pattern from one Makefile variable, `RELEASE_SPECS`, so the two sets can't drift apart. `scripts/browser-split.test.mjs` (in `npm test`) reads both selections from the Makefile with `make -n`, lists each with Playwright's list mode (no browser, about 1 s a run) and checks they don't overlap and together are the whole suite, and that `--project timing` holds exactly the `@timing` tests, so a typo in a project's pattern can't quietly retry a limit check
- Retries: 1 in CI (a failed browser test runs once more), 0 elsewhere and for `@timing` tests, which are limit checks and fail on their first failure. `playwright.config.ts` has two projects, `timing` (`@timing`) and `browser` (the rest); each test is in exactly one, and `npx playwright test --list --project <name>` lists one. The screenshots config keeps 0
- `make meter`: renders the meter bar's images with a local browser that has WebGL. Run on purpose, on the Mac, like `make room`. CI does not run it. Run it through `heavy`; running it again at the same commit leaves `git status --short src/assets/meter` empty. `src/meter-layers.test.ts` checks the committed images against the layer list, and `src/meter-device.test.ts` the mapping from a reading to the layers shown
- `make resume`: builds `public/resume.pdf` from `resume/resume.tex` with tectonic. Run on the Mac; the first run downloads a TeX bundle, so it needs the network. CI does not run it. `src/resume.test.ts` checks the PDF exists and the source has no phone number
- `make og-image`: takes `public/og-image.png`, the link preview image, with a local browser that has WebGL (builds the site, serves it with `npm run preview` on `TEST_PORT`). Run on purpose, on the Mac, through `heavy`. CI does not run it. `src/page-image-tags.test.ts` checks the file exists and its PNG header's size matches the head's `og:image` width and height
- `make favicon`: makes `public/favicon.png` (48×48) and `public/apple-touch-icon.png` (180×180) from the meter's committed images in a local browser. Run on purpose, on the Mac, through `heavy`, and again after `make meter`. CI does not run it. `src/page-icon-tags.test.ts` checks each file's PNG header size and the head's icon links; `scripts/check-budget.test.mjs` checks the icon links don't count toward the first screen
- `make photo SRC=<source image>`: prepares a page image with Python 3 and Pillow. The source is any image Pillow reads (a PNG or a JPEG). With only `SRC` it writes `src/assets/adham.jpg`, the About me portrait (crop, greyscale, contrast stretched, darkened edges, 600 px tall, quality 78, no metadata). With `OUT=<name.jpg> WIDTH=<px> CAP=<KB>` it writes `src/assets/<name.jpg>` instead: a greyscale JPEG with no metadata, contrast stretched (darkest point to black, lightest to white) but no darkened edges (the portrait's only), never scaled up and no wider than `WIDTH`, at the highest quality from 78 down to 50 that is within `CAP`. It fails, saying so and writing nothing, if it can't get within `CAP` by quality 50. `CROP=<left,top,right,bottom>` (source pixels) keeps only that part of the source. `PREVIEW=<png>` also writes a phosphor-green copy for looking. Run on purpose, on the Mac. CI does not run it, and the source is never committed. `src/photo-metadata.test.ts` checks a table of images (file, largest width or height, size cap; one row per page image, the portrait's is 600 px and 60 KB, the MediaSafe screenshot's 1400 px and 200 KB). It also checks that every image the content names has a row: each file exists in `src/assets/`, has no APP1, APP13 or COM segment, is greyscale and is within its caps. It also checks that nothing follows the JPEG's end (EOI marker), and that `IMAGE_FILES` (`src/text/image-files.ts`, the map the panel draws its images from) has an entry for every image the content names, with the width and height the file's own frame header gives. It also builds JPEGs with an EXIF block, bytes after EOI, over a cap and in colour, to check the checker isn't blind. A new image adds a row there and an entry in `IMAGE_FILES`
- `make facts`: every path, command and tag the docs name exists

## What CI runs
CI runs on every branch except `staging` and `production`, including `main` after each merge. CI runs no browser specs (#352): a PR's browser job delayed its review, so the release runs them all, the release specs before staging moves and the light specs after (see below), and a failure is found and fixed there. The release runs only when started by hand, so those specs run on `main` only then, not on each merge. This partly reverses #323: a breakage in a page a PR didn't touch is no longer caught before the merge. The builder still runs the light browser specs it touched in its own session. Nothing waits for the run on `main`. The runner takes 3 jobs at a time (adham/core-infra#5; at 2 jobs, release runs 526 and 527 overlapped and took 859 s and 795 s, against about 450 s alone), so a release's `@timing` and `@render` specs fail on correct code when other jobs share it (#349). A release job therefore runs alone: see "The runner gate" below. With no open PR, the posting steps log that there is nothing to post and pass, except on `main`: there each failure report is added as a new comment on the standing "CI failures on main" issue (created or reopened if needed).
- `frontend`, `backend`, `integration`: the make targets of the same name
- `frontend` also runs `scripts/slow-tests.mjs` after `make frontend` (#416): `make frontend` runs `npm test` with vitest's JSON reporter as well, writing it into the gitignored `test-results` directory (the path is in the `Makefile` recipe), and the script prints a `::warning::` line (file, test name, duration) for each unit test over 1000 ms, slowest first, so it shows in the job's annotations. A unit sweep once ran near vitest's 5000 ms default and timed out on the busy runner while it still passed (#403); this warns before that. The step has `if: always()` and `continue-on-error: true`, and the script exits 0 on a missing report, so it never changes the job result. `scripts/slow-tests.test.mjs` (in `npm test`) feeds it fixture reports with a slow and a fast test, and reads `ci.yml` and the Makefile to check the step's place and the report path
- `gate`: runs the runner gate for `ci-image`, whose build job runs in the kaniko container and can't run it itself, as in `release.yml`
- `ci-image`: the same build-ci-image call as `release.yml`'s (see below). It only asks the registry, unless the branch changed `ci/`; then it builds that branch's own tag
- `screenshots`: the overview plus every station, at desktop and phone size, posted to the PR. Runs in the CI image (it needs `ci-image`), so it installs no system packages and draws with the same Chromium and Mesa as the release specs. `npx playwright install chromium` stays as a check: it does nothing when the image's browser matches `package-lock.json`
- `secret-scan`: gitleaks over the full history, through adham/ci's secret-scan action (pinned by version and SHA-256)
- `facts`: `make facts`
- Every job starts with the runner gate, right after checkout: `node scripts/runner-gate.mjs ci` waits while a `release.yml` job that started before it is running (see "The runner gate" below). `ci-image` has no steps of its own, so it needs the `gate` job instead

## What release runs
`release.yml` runs only when started by hand (`workflow_dispatch`, #355), never on a merge to `main`: Forgejo's "Run workflow" on `main`, or `POST /repos/projects/lab/actions/workflows/release.yml/dispatches` with `{"ref": "main"}`. A merge doesn't release or move staging; run it again by hand to try again after a flaky failure (Forgejo can't re-run one job). The `staging` job pushes only when the run's commit is `main`'s tip, so a run started on another branch can't move staging. Staging moves only when `image` and `browser` (the release specs) both pass, so a commit whose release specs failed never reaches staging. The light specs run after staging, so a light failure on `main` doesn't hold staging back. Each failure is a comment on the "CI failures on main" issue, and `main` stays red until a fix or a revert merges.
- `image`: builds and pushes the image
- `ci-image`: adham/ci's build-ci-image workflow, which builds and pushes the CI image the browser jobs run in (`ci/Dockerfile`: Chromium, Mesa and Xvfb on a base pinned by digest, so the jobs install nothing), only when the registry doesn't have its tag; otherwise it just asks the registry. The tag is `ci-` and a hash of the files in `ci/`, so a branch with a changed Dockerfile pushes a tag of its own, and the browser jobs take the image name from its output. `scripts/ci-image.test.mjs` (in `npm test`) checks the call, the output, the pinned base, and that the Dockerfile's Playwright version matches `package-lock.json`
- `browser`: the release specs only (`make browser-release`: `@timing` and `@render`), on 3 workers (`playwright.config.ts`). The runner has no GPU, so WebGL draws on Mesa's llvmpipe under Xvfb (a third of SwiftShader's CPU); `tests/webgl.spec.ts` fails it if Chromium falls back to SwiftShader
- Each browser job's last step (`browser` and `browser-light` in `release.yml`), `scripts/browser-report.mjs` (its own script, not `post-ci-failure.mjs`, so its step has its own workflow assertions), reports what the run cost, pass or fail, and never changes the job result. It reads the Playwright JSON report, the job's start file and `loadavg()`. The workflows no longer run it on a PR (the script still can): it would create or update one marked comment (`<!-- ci-browser-report -->`): on a pass the job's time, the load average, flaky tests with their first error, the 10 slowest tests and the median and total `boot-ms`; on a failure a line saying the run failed and linking the failure comment. On `main` it posts only for a pass with at least one flaky test (a comment on "CI failures on main"); a clean pass writes nothing, and a failure's own comment (`post-ci-failure.mjs`) names the flaky tests, so the report posts nothing. A flaky test is one that failed and then passed on a retry (status `flaky` in the report); failure comments never count it as failed. `scripts/browser-report.test.mjs` runs it against fixture reports and a fake Forgejo
- `staging`: moves the `staging` branch to the commit, then warns if the release was slow. When main has moved past the commit, it pushes nothing and the run still passes, but the log line is a `::warning::` and `scripts/staging-skipped.mjs` comments on the standing "CI failures on main" issue (created or reopened if needed): staging did not move, which commit it still runs (read from the image tag on the `staging` branch's head, which the move step passes out as `seen` and `runs`) and that a new release on main is needed, since nothing else will move it. That step is best effort (`continue-on-error`; a failed API call is logged and exits 0). `scripts/staging-skipped.test.mjs` runs it against a fake Forgejo: a skip posts the comment, a move posts none, a failing or unreachable Forgejo still exits 0. A release can't run on a PR, so that test is the proof
- `browser-light`: needs `staging` and runs only when staging moved (the `staging` job's `moved` output is `true`; not when main had moved past the commit: that release is out of date, so start a new one on main). Runs the light specs (`make browser-light`) with the same setup, failure posting and report as the `browser` jobs, so within one release they don't share the runner with the `@timing` specs. Nothing waits for it. A failure is a comment on "CI failures on main", and `main` stays red until a fix or a revert merges
- The release clock runs from the release run's start (Forgejo's runs API, by the API run id, not the run number) to the end of the staging push. `scripts/release-clock.mjs` warns, as a comment on the standing "Browser job times" issue (created or reopened if needed), exactly when staging moved, the `browser` job retried no test (a test with more than one result in its Playwright JSON report, flaky or not) and the clock is over 360 s. The comment carries the clock, the browser job's load average and the runner wait in seconds. The warning step is best effort and never blocks staging. `scripts/release-clock.test.mjs` sweeps the rule over time, retried and moved; if the job's token can't read the runs API, the clock starts at the earlier of the `image` and `browser` job starts

- The `gate` job runs first and `image` and `ci-image` need it, and `browser` needs `ci-image`: the runner gate (see below) for the whole release. `image` and `ci-image` have no gate step of their own, since they run in the kaniko container, which has no node and no checkout. Within one release run, `image` (the kaniko build) and `browser` (the release specs) still run at the same time, because a run's own jobs don't block each other. `browser`, `staging` and `browser-light` start with a gate step too, since a CI job can start in the seconds between the `gate` job ending and them starting

## The runner gate
A release job is the only job running on the runner (#361, Adham's decision on 2026-11-17). Forgejo has no exclusive job and a job can't pause the runner, so the jobs coordinate through the API: the gate step reads `GET /repos/{owner}/{repo}/actions/tasks?status=running` with the job's own token (`secrets.GITHUB_TOKEN`) and decides. `scripts/runner-gate.mjs` holds the rule as one pure function, `decide`, and `scripts/runner-gate.test.mjs` (in `npm test`) tests it.
- A release job (`gate`, `browser`, `staging`, `browser-light`) waits until no other job is running in the repo that started before it and isn't part of its own run (same workflow and run number). Jobs that started after it are ignored.
- A CI job (every `ci.yml` job) waits while a `release.yml` job that started before it is running. This is narrower than "while any release job is running": a CI job that was already running when a release job started gets to finish, and the release job waits for it, so it must not wait for that release job back.
- One order covers all jobs: earlier start second first; in the same second a release job comes before any other job; then the lower task id. A job only waits for a job ahead of it, so two jobs can never wait for each other, including two that start in the same second. The tests sweep every pair of kinds, start offsets and id orders for this. Between two release jobs a CI job may run; it never runs at the same time as one.
- It polls every 10 s and gives up, failing the job, after 60 minutes of waiting, saying what it waited for. Three failed reads in a row of the task list (a token that can't read it gives HTTP 403) also fail the job. A waiting job holds a runner slot and uses no CPU.
- Each gate logs one line in the job log: `runner gate: release job waited 100 s for ci.yml #700 frontend, then went`, or `... did not wait`. Time spent waiting in a gate counts toward the release clock (it runs from the run's start), and the gate's log line says how long it waited. A CI job's or a browser job's own time in its report includes its wait, since its gate comes after `Record start time` and checkout.
- The gate comes right after `actions/checkout`, not first: the script is in the repo. A failed gate isn't in a failure comment's `STEPS`, so that comment names the job as the failed step; the reason is in the job log.
- Not covered: `adham/project-template`'s CI also uses the runner, and its jobs don't wait. A job waiting in a gate for a release job that never ends (a crashed runner) fails after 60 minutes. A `promote.yml` job has no gate: it can run beside a release job, but a release job started after it waits for it.
- Release jobs run only when started by hand, so the gate on a release job can't be seen running on a PR. The unit tests are its proof, and the first release after the change is its first real run.

`promote.yml` moves `production`, run by Adham. It takes a release version (`2026.11.20.1`), a commit sha, or nothing for what staging runs, and writes the tag, the digest and the version into `deploy/values-production.yaml`, so production runs `lab:<sha>@<digest>`. A digest it can't find in the registry (an image cleaned up) stops it. `scripts/deploy-image.mjs` does the work for both: the release's gate job works out the version (the Toronto date and a counter past the day's last tag), the image job records the digest kaniko pushed and labels the image (`org.opencontainers.image.revision`, `source`, `version`, `created`), and the staging job writes all three into `deploy/values-staging.yaml` and tags the commit. `scripts/deploy-image.test.mjs` (in `npm test`) tests the version, the values writing and reading, the promote input rules and the registry lookup against fakes, and reads both workflows and the chart for the wiring
