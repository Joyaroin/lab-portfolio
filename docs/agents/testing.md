# Testing facts

Checked against the code on 2026-11-17, and `make facts` run. Each line was last confirmed line by line on 2026-11-10; on 2026-11-17 only the runner's job count (3 at a time) was checked again. The table's "Where it runs" column and the CI and release sections were checked again on 2026-11-17, when PR CI stopped running browser specs (#352): the release runs them all, the release specs before staging and the light specs after.

## Kinds of test
| Kind | How to select it | Where it runs |
|---|---|---|
| Unit | `npm test` | Builder and CI |
| Light browser | `make browser-light PW_ARGS=<spec>` for the specs it touched. `make browser-light` alone only for a change to shared code, through `heavy` | Builder (the specs it touched), and the release's `browser-light` job after staging. PR CI doesn't run it |
| Timing | `@timing` | The release's `browser` job, before staging. In the session only to measure or break-check, through `heavy`, 1 worker. Exact durations are unit tests that pass the time in or fake the clock (`src/frames.test.ts`, `src/tear.test.ts`, `src/nixie.test.ts`, `src/meter-power.test.ts`, `src/shift/shift.test.ts`, `src/ambient/redraw.test.ts`); browser timing specs check that a play happened, its order, and the safe side of a limit |
| Heavy rendering | `@render` | The release's `browser` job, before staging |

## Commands
- `make frontend`: `npm ci`, the typecheck, `npm test` and the build
- `npm run build`: runs `scripts/save-gap.mjs` and `scripts/save-commits.mjs` before the type check. Each reads GitHub anonymously with a 5 s timeout and writes a gitignored `src/*-saved.local.json`. A failed call keeps the saved file: the newer of the local and committed files by `savedAt`, so a build offline or past the rate limit still leaves a valid file. `COMMITS_API=<url>` replaces the commits URL, for the offline run: `COMMITS_API=https://invalid.example heavy npm run build`. Run builds through `heavy`
- `make integration`: `make frontend`, then the integration test
- `make browser`: the full Playwright suite. Installs browsers and system packages only in CI. CI never runs it whole: the release runs the two selections below
- `make browser-light`: the `browser` recipe without the release specs. Passes `PW_ARGS` through
- `make browser-release`: the `browser` recipe with only the release specs, `@timing` or `@render`. Passes `PW_ARGS` through. Both targets take the pattern from one Makefile variable, `RELEASE_SPECS`, so the two sets can't drift apart. `scripts/browser-split.test.mjs` (in `npm test`) reads both selections from the Makefile with `make -n`, lists each with Playwright's list mode (no browser, about 1 s a run) and checks they don't overlap and together are the whole suite, and that `--project timing` holds exactly the `@timing` tests, so a typo in a project's pattern can't quietly retry a limit check
- Retries: 1 in CI (a failed browser test runs once more), 0 elsewhere and for `@timing` tests, which are limit checks and fail on their first failure. `playwright.config.ts` has two projects, `timing` (`@timing`) and `browser` (the rest); each test is in exactly one, and `npx playwright test --list --project <name>` lists one. The screenshots config keeps 0
- `make meter`: renders the meter bar's images with a local browser that has WebGL. Run on purpose, on the Mac, like `make room`. CI does not run it. Run it through `heavy`; running it again at the same commit leaves `git status --short src/assets/meter` empty. `src/meter-layers.test.ts` checks the committed images against the layer list, and `src/meter-device.test.ts` the mapping from a reading to the layers shown
- `make resume`: builds `public/resume.pdf` from `resume/resume.tex` with tectonic. Run on the Mac; the first run downloads a TeX bundle, so it needs the network. CI does not run it. `src/resume.test.ts` checks the PDF exists and the source has no phone number
- `make og-image`: takes `public/og-image.png`, the link preview image, with a local browser that has WebGL (builds the site, serves it with `npm run preview` on `TEST_PORT`). Run on purpose, on the Mac, through `heavy`. CI does not run it. `src/page-image-tags.test.ts` checks the file exists and its PNG header's size matches the head's `og:image` width and height
- `make favicon`: makes `public/favicon.png` (48×48) and `public/apple-touch-icon.png` (180×180) from the meter's committed images in a local browser. Run on purpose, on the Mac, through `heavy`, and again after `make meter`. CI does not run it. `src/page-icon-tags.test.ts` checks each file's PNG header size and the head's icon links; `scripts/check-budget.test.mjs` checks the icon links don't count toward the first screen
- `make photo SRC=<source image>`: prepares a page image with Python 3 and Pillow. The source is any image Pillow reads (a PNG or a JPEG). With only `SRC` it writes `src/assets/adham.jpg`, the About me portrait (crop, greyscale, contrast stretched, darkened edges, 600 px tall, quality 78, no metadata). With `OUT=<name.jpg> WIDTH=<px> CAP=<KB>` it writes `src/assets/<name.jpg>` instead: a greyscale JPEG with no metadata, contrast stretched (darkest point to black, lightest to white) but no darkened edges (the portrait's only), never scaled up and no wider than `WIDTH`, at the highest quality from 78 down to 50 that is within `CAP`. It fails, saying so and writing nothing, if it can't get within `CAP` by quality 50. `CROP=<left,top,right,bottom>` (source pixels) keeps only that part of the source. `PREVIEW=<png>` also writes a phosphor-green copy for looking. Run on purpose, on the Mac. CI does not run it, and the source is never committed. `src/photo-metadata.test.ts` checks a table of images (file, largest width or height, size cap; one row per page image, the portrait's is 600 px and 60 KB): each file exists in `src/assets/`, has no APP1, APP13 or COM segment, is greyscale and is within its caps. It also builds JPEGs with an EXIF block, over a cap and in colour, to check the checker isn't blind. A new image adds a row
- `make facts`: every path, command and tag the docs name exists
- A flash limit spec counts the tear's visible snap back (the displacement map's scale reaching 0, `tests/lib/snap.ts`), never the filter coming off. `src/tear-draw.test.ts` checks the view leaves scale 0 on its last frame, whatever the frame rate, and on its stop path (a tear cut short)
- `tests/idle.spec.ts` checks the room's idle rule. At rest, at a station, in portrait (390×844) and under reduced motion, nothing draws; at the landscape overview the ambient screens keep drawing (ADR 0007), so the `@timing` power-on test runs at a portrait size, where they hold a still frame, to see the power-on stop. Three more `@timing` tests there compare screenshots over two seconds: they change at the landscape overview (so the comparison can see the screens), and don't at a station or under reduced motion
- `tests/shift.spec.ts` records the snap back's measured time as a `snap-back-ms` test annotation and a log line, for the release browser job's report
- `openTour` (`tests/lib/page.ts`) records how long its `goto` and boot took as a `boot-ms` test annotation. A spec's own `page.goto` isn't measured. A test that calls `openTour` twice has two annotations, which the report adds up; the report's median and total cover annotated tests only, and it says how many. This is the measurement for sharing one booted page per worker (#321, phase 2)
- A browser spec can't import `src/meter-layers.ts` (Playwright's loader refuses JSON modules); `tests/device.spec.ts` reads `src/assets/meter/layers.json` itself
- `tests/boot.spec.ts`'s `slowModel` helper serves the room model from a local server and waits on CDP `Network.dataReceived` for each chunk. That server must answer only `/room.glb`: on the Mac a stray `GET /` sometimes reaches it, and taking it for the model sent later chunks to a dead response, so the wait timed out (a chunk behind, or at 0) in whole-file runs only. The slow-load test needs the whole file to show it: `heavy make browser-light PW_ARGS="tests/boot.spec.ts --repeat-each=5"`
- `waitForCamera` (`tests/lib/page.ts`) asks the scene for a frame before each read (a `pointermove` on `window`, which only the room's redraw hears) and waits for `data-camera` to be written. The scene draws on demand and writes `data-camera` per drawn frame, so a plain read can't tell a camera at rest from one whose next frame is late: slow frames under load gave two equal reads mid-ease (#330). Read the camera at rest with it, not with `waitUntilStill` over `data-camera`. `tests/wait-until-still.spec.ts` delays every frame to check it
- `tests/fold.spec.ts` (a light spec) opens MediaSafe, Off the keyboard and Home lab at 1280×720, 1440×900 and 1920×1080 and checks the "more" cue (`data-more`) isn't showing and the panel's `scrollHeight - clientHeight` is at most 4, the cue's own threshold (`src/text/more.ts`). It waits for every `img` in the panel to load or fail first. A page is one entry in its `PAGES` list: `extraLines` adds that many lines under the bullets (the break check, or a spare-line check), and `fixme` marks a known failure (Home lab, until #343). A later ticket edits only its own page's entry
- `tests/links-row.spec.ts` (a light spec) checks a page with no links draws no links row (`data-links`: Why I do this and Off the keyboard) and a page with links draws one holding exactly its links (Contact, Software factory). The break check is to draw the row always
- One spec in the session: `heavy npx playwright test tests/<spec> --workers=1`

## What CI runs
CI runs on every branch except `staging` and `production`, including `main` after each merge. CI runs no browser specs (#352): a PR's browser job delayed its review, so the release runs them all, the release specs before staging moves and the light specs after (see below), and a failure is found and fixed there. The release runs only when started by hand, so those specs run on `main` only then, not on each merge. This partly reverses #323: a breakage in a page a PR didn't touch is no longer caught before the merge. The builder still runs the light browser specs it touched in its own session. Nothing waits for the run on `main`. The runner takes 3 jobs at a time (adham/core-infra#5; at 2 jobs, release runs 526 and 527 overlapped and took 859 s and 795 s, against about 450 s alone), so a hand-started release's `browser` job (the `@timing` and `@render` specs) can share it with PR jobs; the release clock shows how often. With no open PR, the posting steps log that there is nothing to post and pass, except on `main`: there each failure report is added as a new comment on the standing "CI failures on main" issue (created or reopened if needed).
- `frontend`, `backend`, `integration`: the make targets of the same name
- `screenshots`: the overview plus every station, at desktop and phone size, posted to the PR
- `secret-scan`: gitleaks over the full history
- `facts`: `make facts`

## What release runs
`release.yml` runs only when started by hand (`workflow_dispatch`, #355), never on a merge to `main`: Forgejo's "Run workflow" on `main`, or `POST /repos/projects/lab/actions/workflows/release.yml/dispatches` with `{"ref": "main"}`. A merge doesn't release or move staging; run it again by hand to try again after a flaky failure (Forgejo can't re-run one job). The `staging` job pushes only when the run's commit is `main`'s tip, so a run started on another branch can't move staging. Staging moves only when `image` and `browser` (the release specs) both pass, so a commit whose release specs failed never reaches staging. The light specs run after staging, so a light failure on `main` doesn't hold staging back. Each failure is a comment on the "CI failures on main" issue, and `main` stays red until a fix or a revert merges.
- `image`: builds and pushes the image
- `browser`: the release specs only (`make browser-release`: `@timing` and `@render`), on 3 workers (`playwright.config.ts`). The runner has no GPU, so WebGL draws on Mesa's llvmpipe under Xvfb (a third of SwiftShader's CPU); `tests/webgl.spec.ts` fails it if Chromium falls back to SwiftShader
- Each browser job's last step (`browser` and `browser-light` in `release.yml`), `scripts/browser-report.mjs` (its own script, not `post-ci-failure.mjs`, so its step has its own workflow assertions), reports what the run cost, pass or fail, and never changes the job result. It reads the Playwright JSON report, the job's start file and `loadavg()`. The workflows no longer run it on a PR (the script still can): it would create or update one marked comment (`<!-- ci-browser-report -->`): on a pass the job's time, the load average, flaky tests with their first error, the 10 slowest tests and the median and total `boot-ms`; on a failure a line saying the run failed and linking the failure comment. On `main` it posts only for a pass with at least one flaky test (a comment on "CI failures on main"); a clean pass writes nothing, and a failure's own comment (`post-ci-failure.mjs`) names the flaky tests, so the report posts nothing. A flaky test is one that failed and then passed on a retry (status `flaky` in the report); failure comments never count it as failed. `scripts/browser-report.test.mjs` runs it against fixture reports and a fake Forgejo
- `staging`: moves the `staging` branch to the commit, then warns if the release was slow
- `browser-light`: needs `staging` and runs only when staging moved (the `staging` job's `moved` output is `true`; not when main had moved past the commit: that release is out of date, so start a new one on main). Runs the light specs (`make browser-light`) with the same setup, failure posting and report as the `browser` jobs, so within one release they don't share the runner with the `@timing` specs. Nothing waits for it. A failure is a comment on "CI failures on main", and `main` stays red until a fix or a revert merges
- The release clock runs from the release run's start (Forgejo's runs API, by the API run id, not the run number) to the end of the staging push. `scripts/release-clock.mjs` warns, as a comment on the standing "Browser job times" issue (created or reopened if needed), exactly when staging moved, the `browser` job retried no test (a test with more than one result in its Playwright JSON report, flaky or not) and the clock is over 360 s. The comment carries the clock, the browser job's load average and the runner wait in seconds. The warning step is best effort and never blocks staging. `scripts/release-clock.test.mjs` sweeps the rule over time, retried and moved; if the job's token can't read the runs API, the clock starts at the earlier of the `image` and `browser` job starts

`promote.yml` moves `production`, run by Adham.
